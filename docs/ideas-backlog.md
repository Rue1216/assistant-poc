# 對話介面構想清單

> 2026-10-22 整理。尚未設計，排定時程後各自走規格 → 計畫流程。
> 已有規格：想法 1 → [回答引用](superpowers/specs/2026-10-22-answer-citations-design.md)；想法 3、4 → Prompt 評測集（下一份規格）。

| # | 構想 | 現況 | 初步看法 |
|---|---|---|---|
| 2 | 前端呈現處理步驟，改善等待體感 | 只有固定文字「正在查詢資料並整理回答…」 | 不能顯示模型的原始推理（API 不提供，也可能洩漏系統提示），但可以顯示工具步驟，例如「查詢顧客持股 → 查詢台積電行情」。需要串流（SSE）；要先確認平台「統一同步回傳」的原則是否允許，以及 Nginx 要關閉 buffering。成本較低的替代做法：依經過時間切換提示文字 |
| 3 | 顯示 token 使用量 | 後端計算每次提問的 token，超過 16,000 中止（`AI_TOKEN_BUDGET_EXCEEDED`），輸出上限 1,000；不存稽核、不顯示 | OpenAI 的限制是專案或 key 的速率上限與預算上限。建議把輸入、輸出 token 記進稽核，只給管理者看；併入 Prompt 評測集（需要「平均 Token 使用量」） |
| 4 | 回覆的 like / dislike 與可量化的 prompt 評測 | 沒有 | 即時回饋（綁 `requestId`）和離線評測集（固定問答比較版本）互補；併入 Prompt 評測集規格 |
| 5 | 提醒離開對話會遺失紀錄；超過輪數上限時自動摘要 | 對話存在瀏覽器記憶體，換顧客、重整、登出就清空；超過 10 輪或 8,000 字時較早的內容**直接捨棄、沒有提示** | 至少先在畫面上提示「較早的對話不再參考」。自動摘要要多一次 GPT 呼叫（費用），摘要內容也要去識別化審查，適合之後的版本 |
| 6 | 依操作情境推薦提問，取代一次列出所有範例 | 快捷問題來自 System Instructions 的範例問題，依 5 個分類分組 | 推薦什麼取決於所在頁面和顧客資料，和想法 7 一起設計 |
| 7 | 不同頁面或服務可用的工具不同（個人 360、客群 360…） | 小幫手只在個人 360 頁面，工具固定 7 個 | 新增「情境」概念：頁面傳入情境代碼，後端依情境決定可用工具、問題分類與推薦提問。牽涉 API、Prompt 管理與權限，規模最大，另開規格 |
